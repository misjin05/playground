1. 이번 실험이 보여준 4가지 핵심 시사점

- Fresh Context + Atomic Task = 높은 1차 통과율

PRD.md에서 태스크를 1개씩 꺼내 매번 새 세션으로 구현하고 unittest 통과 후 커밋(T1→T2→T3→T4)한 결과, MaxIterations=10 중 재시도 없이 4회 만에 27개 테스트 100% 통과로 종료되었습니다.
긴 대화 컨텍스트에 시행착오를 누적시키는 것보다, 작은 완료 단위 + 깨끗한 컨텍스트가 구현 안정성을 크게 높입니다.

ralph의 본질: 거대한 라이브러리가 아니라 "while 루프 + 새 컨텍스트(Fresh Context) + 테스트 통과 후 종료" 라는 아주 단순한 패턴입니다. (실제로 이번에 쓰신 ralph.ps1도 47줄이었습니다.)

- 루프의 성패는 "루프 밖 앞단(Spec & Gate)"에서 결정된다

루프가 흔들리지 않은 이유는 앞단(design_draft.md → goldfish_review_report.md → mdcheck.md)에서 시그니처·엣지 케이스·테스트 기준을 모호함 없이 고정했기 때문입니다.
즉, 좋은 Loop Engineering은 루프 코드만 잘 짜는 것이 아니라 검증 가능한 완료 조건(Acceptance Criteria)을 먼저 고정하는 것입니다.

- 테스트 통과(Self-Verification) ≠ 코드 리뷰 완료

unittest는 27개 모두 통과했지만, 정작 .gitignore 누락으로 __pycache__/*.pyc 바이너리가 T1~T3 커밋에 전부 포함되는 문제가 발생했습니다.
테스트는 "기능 동작"만 검증할 뿐 커밋 위생, 컨벤션, 보안, 불필요한 변경, 구조적 중복은 잡지 못합니다. 사용자 VOC인 "턴별 코드리뷰 + 테스트 한 세트"를 만족하려면 테스트 게이트 뒤에 Diff 기반 리뷰 게이트가 별도로 필요합니다.

- 자율 루프의 실제 병목은 모델보다 Harness(권한·쉘·안전장치):권한 제어 (거버넌스)

이번 실험에서도 모델 성능이 아니라 ① PowerShell 실행 정책, ② 다중행/따옴표 인자 파싱 오류, ③ Headless 모드의 write_file 자동 거부(settings.json allowlist 필요)에서 초기 마찰이 발생했습니다.
자체 어시스턴트에서도 도구 권한 정책, OS/쉘 호환성, 무한 루프 상한(MaxIterations)이 먼저 단단해야 루프가 굴러갑니다.
"테스트 실행·파일 읽기·워크스페이스 내 수정은 자동 허용하고, 외부 전송이나 삭제 같은 위험한 명령만 사용자에게 묻는 규칙"이 미리 정해져 있어야 멈추지 않습니다.

진행 방향 

Track 1. 자율 배치 / 멀티태스크 파이프라인 (Cline CLI + Ralph 오픈소스)

스펙(PRD) 기반으로 여러 태스크를 끊김 없이 구현·검증·커밋하는 트랙

적용 대상: 기능 단위 PRD 구현, 마이그레이션, 테스트 대량 보강 등 다단계 자율 작업
구현 방식:
ralph / ralph-tui 오픈소스에 Cline CLI 어댑터를 연결해 오케스트레이터로 활용
태스크 1개마다 Fresh Context로 Cline CLI를 단발 실행 → 테스트 통과 확인 → 커밋 후 다음 태스크 진행
기대 효과: 루프 엔진과 실시간 진행률/스트림 로그 대시보드(ralph-tui)를 직접 개발하지 않고 빠르게 확보


Track 2. 일상 IDE 대화형 코딩 (Cline 코어 Turn-level Hook, 핵심 VOC 대응)

사용자가 IDE에서 요청하는 매 수정 턴마다 "코드리뷰 + 테스트 한 세트"를 보장하는 트랙

적용 대상: IDE 채팅에서의 일상적인 기능 수정, 버그 픽스, 리팩토링 요청
구현 방식:
파일 변경이 발생한 턴에 한해 attempt_completion(턴 종료) 직전 내부 훅/게이트 실행 (단순 질의응답 턴은 스킵):
Test Gate: 변경 범위 관련 테스트·린트 자동 실행 → 실패 시 에러 로그 기반 Self-Repair 루프(최대 N회)
Review Gate: git diff를 대상으로 Fresh Context 경량 리뷰어 호출 (로직 결함, 컨벤션, 보안, .pyc 등 불필요 파일 혼입 점검) → 지적 사항 발생 시 수정 후 Test 재검증
UI에 현재 단계([구현] → [테스트] → [리뷰]) 상태 표시
기대 효과: 대화 맥락을 유지하면서도 "테스트만 통과하고 리뷰가 빠지거나, 수정 후 검증 없이 끝나는" VOC 해소
