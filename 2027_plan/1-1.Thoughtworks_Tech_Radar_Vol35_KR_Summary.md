## 1. 긍정적인 항목 — `Adopt` / `Trial` 핵심 Top 3 (DP-01 ~ DP-04 직결)

### 1) `5. Progressive context disclosure` (`Adopt`, Techniques · 16p) → *DP-02 · DP-04 직결*
* **내용**: LLM에 모든 규칙·문서·도구를 한꺼번에 밀어 넣지 않고, 핵심 맥락만 먼저 로드한 뒤 필요 시점에만 추가 컨텍스트(문서 링크·MCP 툴·스킬 등)를 단계적으로 불러오는 Context Engineering 기법. 토큰 비용 절감과 문맥 오염(Context rot) 방지를 위해 **`Adopt`(기본값)**로 승격.
* **함께 볼 `Trial` 기법·도구**:
  * **`8. Agent-maintained knowledge bases` (`Trial`, 17p)**: 팀 공유 지식을 링크된 마크다운 파일로 두고 **코딩 에이전트가 직접 유지·갱신**하며 함께 조회하는 방식.
  * **`83. OpenWiki` (`Trial`, 43p)**: 소스 코드 변경을 감지해 코드베이스용 마크다운 위키를 **자동 생성·체크포인트 기반 최신화**해 에이전트 컨텍스트로 제공하는 CLI 도구.
* **2027년 적용**:
  * **DP-02**: 레포 영속 메모리의 **자동 축적·최신화 + 선별 맥락 주입(Selective Context Injection)** 설계에 적용.
  * **DP-04**: 도구·MCP·Skill을 일괄 주입하지 않고 **작업에 필요한 것만 동적 바인딩**하는 설계 근거 *(Vol. 35 `62. Decision models`, `Assess` 35p와 연계 탐색)*.

### 2) `10. Coding harness for general-purpose agents` (`Trial`, Techniques · 17~18p) + `69. OpenAI Codex` / `70. OpenCode` (`Adopt`, Tools · 39p) → *DP-03 직결*
* **쉽게 이해하기**: 문서 처리·운영 지원·마이그레이션 계획 같은 범용 업무 에이전트를 만들 때, LangGraph 같은 프레임워크로 실행 루프·세션 관리·컨텍스트 압축을 바닥부터 직접 짜지 않고 **이미 검증된 코딩 에이전트의 런타임(Headless/Server 모드·SDK)을 그대로 실행 엔진으로 재사용**하는 패턴.
  * **재사용 가능한 핵심 기능**: 장시간 작업 시 컨텍스트 자동 압축(Compaction), 세션 영속화, Headless 실행, 파일·터미널 도구 호출, 스킬·서브에이전트 기능.
  * **대표 런타임**: `Claude Agent SDK`, `Codex SDK / app-server`, `OpenCode server/SDK`, `Pi SDK/RPC` *(참고: `Claude Code`는 이전 호에서 이미 Adopt를 거쳐 이번 호 목록에서는 빠졌으며, `69. OpenAI Codex`·`70. OpenCode` 본문 39p에 CLI-first 표준 코딩 에이전트로 나란히 언급됨.)*
  * **주의점(18p)**: 코딩 하네스의 기본 시스템 프롬프트는 "코드 작성·실행"에 편향되어 있고 기본 프롬프트가 커서 토큰 소모가 많을 수 있으므로, 도메인에 맞게 기본 프롬프트·권한을 조정하고 비용을 모니터링해야 함.
* **2027년 적용 (DP-03 — Agent Driver Adapter)**:
  * 외부 SDK 소스코드를 우리 레포에 가져와 유지보수할 필요 없이, **1단계(MVP)에서는 사내에 설치된 `claude`·`codex` CLI를 Headless 서브프로세스로 호출하는 얇은 어댑터**로 단일 런타임(`@cline/agents`) 종속을 탈피.
  * **중기 표준화**: 생태계 성숙 추이에 따라 Vol. 35의 **`57. Agent Client Protocol (ACP)`** *(Assess, 33p — JSON-RPC 기반 에이전트 제어 표준)*로 전환 검토.
* **참고자료 (공식 문서)**:
  * [Thoughtworks Blip 원문](https://www.thoughtworks.com/radar/techniques/coding-harness-for-general-purpose-agents) · [Martin Fowler — Harness Engineering](https://martinfowler.com/articles/harness-engineering.html)
  * [Anthropic — Building agents with the Claude Agent SDK](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk)
  * [OpenAI Codex (CLI/SDK/app-server)](https://github.com/openai/codex) · [OpenCode SDK](https://opencode.ai/docs/sdk/) / [Server](https://opencode.ai/docs/server/)
  * [Agent Client Protocol (ACP)](https://agentclientprotocol.com/) · [codex-acp 구현체](https://github.com/agentclientprotocol/codex-acp)

### 3) `11. Feedback flywheel` (`Trial`, 18p) & `18. Self-improving harness` (`Trial`, 20p) → *DP-01 · DP-02 직결*
* **내용**:
  * **`11. Feedback flywheel` (`Trial`, 18p)**: 세션 종료마다 반복 실패한 체크(**Feedback sensors**)와 수정 사항을 공유 규칙·하네스에 되먹임하는 구조. Thoughtworks는 *"하네스 개선이 이제 일상이 되어 `Trial`로 승격"*했다고 명시.
  * **`18. Self-improving harness` (`Trial`, 20p)**: 에이전트가 **실행 트레이스와 평가 피드백을 직접 분석해 프롬프트·컨텍스트 전략·워크플로우·메모리를 스스로 개선**하는 닫힌 루프 하네스.
* **2027년 적용 (DP-01)**: 실패 피드백 정제 및 자가 개선 루프(`11`, `18`)를 **Executor–Verifier 자율 완결 루프(Built-in Verifier StepAgent)**와 영속 메모리에 내재화.

> **용어 참고 — `Feedback sensors` (피드백 센서)**  
> 코딩 에이전트 실행 루프 안에서 사람에게 넘어가기 전에 오류·규칙 위반을 기계적으로 감지해 에이전트에게 즉시 되돌려주는 자동 체크 장치(빌드·테스트·린터·AST 검사·`94. Habit Hooks` 등). 우리 계획의 **DP-01 Layer 1 기계적 자동 체크 + Verifier의 구조화된 Fix Report 주입**에 해당.

## 2. Techniques `Adopt` 전체 6개 항목 요약 (15~16p)

| 번호 · 타이틀 | 상태 | 핵심 설명 |
|---|---|---|
| **1. Agent sandboxing** *(15p)* | **New** | AI 에이전트가 코딩을 넘어 시스템 전반에서 자율 실행됨에 따라, 모든 에이전트를 **격리된 환경(최소 권한·외부 접근 제한)**에서 실행하는 것을 기본값으로 권고. 예상치 못한 오작동·악성 악용 시 피해 범위를 차단. |
| **2. Mutation testing** *(15p)* | **Moved in** | 코드에 의도적으로 작은 버그(Mutation)를 심어 테스트가 실제로 실패하는지 검증하는 기법. AI가 **겉보기만 통과하는 부실한 테스트로 커버리지 수치만 부풀리는 문제**를 방지. 최근에는 에이전트가 루프 안에서 변경분만 증분(Incremental)으로 자율 실행 가능. |
| **3. Path-to-production mapping** *(15p)* | **No change** | 개발자 워크스테이션부터 프로덕션 배포까지 전 과정을 매핑해 **대기·재작업·병목 지점을 가시화**하는 기법. 에이전트로 코드 생산량만 빨라지면 하류 병목이 증폭되므로, 코딩 속도가 아니라 End-to-End 흐름 전체를 최적화해야 함. |
| **4. Post-quantum cryptography** *(15~16p)* | **Moved in** | 양자컴퓨터 공격에 대비한 차세대 암호 알고리즘(NIST 표준 확정: ML-KEM, ML-DSA, SLH-DSA). 현재 암호화된 데이터를 먼저 수집해 두었다가 나중에 해독하는 위협에 대비해 키 교환부터 단계적 전환 권고. |
| **5. Progressive context disclosure** *(16p)* | **Moved in** | LLM에 핵심 맥락만 먼저 제공하고, 필요 시점에만 추가 문서·MCP 툴·스킬을 단계적으로 로드하는 Context Engineering 기법. 토큰 비용 절감과 문맥 오염(Context rot) 방지를 위해 `Adopt`로 승격. |
| **6. Threat modeling** *(16p)* | **No change** | 시스템의 잠재적 보안 위협을 체계적으로 식별하는 기법. 특히 생성형 AI의 프롬프트 인젝션·자율 행동처럼 기존 룰 기반 스캔으로 못 잡는 위험을 사전에 찾고, 어디에 결정론적 가드레일을 둘지 정의. |
