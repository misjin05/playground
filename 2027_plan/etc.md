바로 쓰는 /goal 프롬프트 템플릿
text
/goal [로그 경로: 예) ./logs/*.log 또는 /var/log/app/] 에 있는 대용량 로그를 분석하여 시스템 이상(Anomaly)을 탐지하고, 근본 원인(RCA) 리포트를 작성하라.
## 1. 대상 및 배경
- 로그 형식: [예: JSON Lines / Nginx Access Log / Spring Boot 애플리케이션 로그]
- 분석 대상 기간: [예: 2026-11-24 00:00 ~ 23:59, 또는 전체 기간]
- 중점 확인 영역: [예: 응답 지연(latency spike), 5xx 에러 급증, OOM/재시작, 비정상 트래픽/인증 실패]
## 2. 대용량 처리 제약 (필수 준수)
- 원본 로그 파일을 통째로 읽거나(cat 등) 컨텍스트에 대량 출력하지 말 것.
- 먼저 파일 크기, 라인 수, 타임스탬프 범위, 상위 20줄 샘플만 확인하여 스키마를 파악할 것.
- 실제 파싱·집계·탐지는 Python(polars/pandas/duckdb) 또는 awk/rg/jq 스크립트를 작성해 스트리밍/청크 단위로 처리할 것.
- 중간 집계 결과(CSV/Parquet/JSON)와 분석 스크립트는 `./analysis/` 디렉터리에 저장해 재실행 가능하게 유지할 것.
- 원본 로그 파일은 절대 수정하거나 삭제하지 말 것.
## 3. 분석 절차
1. **프로파일링**: 로그 볼륨, 시간대별 분포, 로그 레벨/상태 코드 분포, 주요 필드 결측치 파악.
2. **다각도 이상 탐지**:
   - **시계열 이상**: 1분/5분 단위 버킷으로 에러율, 요청량, p95/p99 지연시간의 급변 구간 탐지 (Rolling Z-score, IQR 또는 변화점 탐지).
   - **패턴/희귀 이상**: 숫자·UUID·IP 등을 마스킹해 로그 템플릿화한 뒤, 특정 시점에 갑자기 등장하거나 급증한 희귀 메시지/스택트레이스 추출.
   - **상관관계 분석**: 이상 발생 시점 전후(±5분)의 선행 이벤트(배포, 타임아웃, DB/외부 API 오류, 리소스 경고 등)를 trace_id/request_id 또는 시간축으로 연결.
3. **검증 및 노이즈 제거**: 단순 헬스체크, 알려진 정기 배치, 봇 트래픽 등 False Positive를 필터링하고 실제 장애/이상 후보만 남길 것.
## 4. 완료 조건 (모두 충족 시 종료)
- `./analysis/anomaly_report.md` 생성 완료. 리포트에는 아래 항목이 반드시 포함되어야 함:
  1. **Executive Summary**: 탐지된 핵심 이상 항목 요약 (심각도 Critical/High/Medium 분류)
  2. **이상 타임라인 표**: 발생 시각, 지속 시간, 영향 범위, 평상시 대비 변화량(정량 수치)
  3. **항목별 근본 원인(RCA) 가설**: 추정이 아닌 **실제 로그 파일명·라인 번호·원문 발췌**를 근거로 제시
  4. **권고 조치**: 즉시 대응 항목 및 재발 방지/모니터링 알람 기준 제안
- 분석에 사용한 재현 가능한 스크립트(`./analysis/run_analysis.py` 등)가 에러 없이 재실행됨을 검증할 것.
- 근거 로그 없이 추측한 내용이 없는지 최종 셀프 체크 후 종료할 것.



잘 작동하게 만드는 핵심 설계 포인트 4가지
1.컨텍스트 보호 규칙 명시 ("통째로 읽지 말 것")
- 대용량 로그에서 가장 흔한 실패 원인은 에이전트가 grep 결과를 수천 줄씩 출력하거나 큰 파일을 직접 읽어 컨텍스트 한도에 걸리는 것입니다.
- "샘플 20줄만 보고 → 스크립트(DuckDB/Polars/Python)로 집계 → 요약 통계만 읽기" 흐름을 강제해야 빠르고 정확합니다.
2. '이상(Anomaly)'을 통계적·패턴 관점으로 분해
- 단순히 "이상한 걸 찾아줘"라고 하면 ERROR 키워드만 grep하고 끝나는 경우가 많습니다.
- 시계열 급변(빈도/지연시간) + 희귀 패턴(템플릿 마스킹) + 전후 상관관계(선행 이벤트) 3축을 지정하면 숨겨진 장애 징후까지 잡아냅니다.
3. 근거 강제 (Hallucination 방지)
- "파일명, 라인 번호, 정량 수치(평소 대비 몇 배)를 반드시 근거로 제시하라"는 조건을 완료 기준에 넣으면 에이전트가 스스로 원본 로그를 재확인하는 검증 루프를 돕니다.
4. 명확한 종료 조건 (Exit Criteria)
- /goal 모드는 목표가 모호하면 끝없이 분석을 늘리거나 반대로 너무 빨리 종료할 수 있습니다. 산출물 파일 경로(anomaly_report.md), 필수 섹션, 스크립트 재실행 검증을 완료 조건으로 못 박는 것이 좋습니다.
