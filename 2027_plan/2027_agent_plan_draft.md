## 1. DP-01. 문제 정의 — 정량적 목표(Goal) 기반 자율 완결 루프 (Spec + Built-in Verifier StepAgent)

### 문제 상황 `(형식적 완료 판정과 YAML 의존적 품질 편차)`
* **[사내 사용자 VOC]** 테스트 생성처럼 목표(커버리지·통과)가 정량적인 작업은 품질이 높으나, 기능 구현·버그 수정·리팩토링 등은 완료 처리된 이후에도 요구사항 누락·오류로 개발자가 다시 손봐야 하는 사례 빈발
* **[기존 완료·재실행 구조의 한계]** 기존 Orchestrator는 `dashboard.md`의 누락(공란) 여부 중심으로 동일 모델을 재실행하며, 결과 확인(`step-verifier`)은 사용자가 YAML에 수동 구성해야 하는 선택 영역이어서 **정량적 목표(Goal) 달성 판정과 실패 원인을 반영한 수렴**을 프레임워크가 일관되게 보장하지 못함

### 해결방법 검토
* **[기존 방식의 한계: YAML 수동 검증 및 단일 에이전트 자가 점검]** 사용자가 매번 `step-verifier`를 YAML에 수동 작성하면 작성자 역량에 따라 품질 편차가 크고 유지보수 비용이 가중됨. 또한 구현 에이전트가 동일 세션에서 자기 코드를 스스로 점검(`/self-review`)하는 방식은 자기 편향과 기존 기능 회귀(Regression)를 유발하는 한계가 확인됨 *(arXiv:2611.01181, 2026.10)*
* **[외부 AI 도구 동향: 목표 지향 자율 완결(`/goal` 패턴) & 폐쇄 루프 하네스]** 최신 코딩 에이전트(Claude Code `/goal` 패턴 등)처럼 작업 전 **완료 목표(Goal/Spec)**를 선언하면 단발 실행으로 멈추지 않고 목표를 충족할 때까지 자율 반복·수정하는 방식으로 진화 중. Gartner 2027 역시 코드가 사람에게 도달하기 전 자동 린트·테스트 게이트(`Automatic delivery backpressure`)와 **`Implement → Verify → Fix/Reject` 폐쇄 루프**를 하네스에 내재화할 것을 권고 *(Top Strategic Technology Trends for 2027, Trend 5)*

### 미해결 시 위험 `(정량 목표 및 내장 Verifier 루프 부재 시)`
* `dashboard.md`상 완료되었으나 실제로는 돌아가지 않거나 의도가 누락된 코드가 양산되어, **개발자 재작업 부담 증가 및 “직접 짜는 게 빠르다”는 인식으로 사내 채택률 정체**
* 테스트 외 일반 개발 영역으로 Craft를 확장할수록 결과 품질이 들쭉날쭉해져 **PR 생산성 향상 효과 확보 불가**

### 핵심 설계 문제
> **“사용자가 매번 YAML로 확인 단계를 짜지 않아도, 구현과 분리된 내장 Verifier StepAgent가 정량적·객관적 목표(Goal) 기준으로 끝까지 확인해 ‘돌아가는 PR’을 스스로 마무리하게 하려면 어떻게 설계해야 하는가?”**
> ▶ 기존 Step 격리 구조 위에 **① 기계적 기본선 체크(Layer 1) · ② 판정 전용 내장 Verifier StepAgent(Layer 2, 코드 수정 금지) · ③ 구조화된 Fix Report 주입 및 한계 도달 시 실패 원인 투명 보고**를 결합한 **Executor–Verifier 자율 완결 루프**를 내재화하여, 모든 Craft에서 일관된 코딩 완결성 보장

#### 참고: v1 Step 격리 → v2 Executor–Verifier 자율 완결 루프
```text
  Orchestrator (L2)
       │
       │  ┌─── Executor–Verifier Loop (최대 N회 · 비용 상한 · 동일오류 정체 감지) ───────────┐
       ▼  ▼                                                                                 │
  [Executor StepAgent (클린 세션 · 구현/수정 전담)]                                           │
   • 입력: memory.md (정량 Goal/Spec) + Verifier의 구조화된 Fix Report (미달 기준·원인)       │
   • 작업: 코드/분석 수행                                                                    │
       │                                                                                    │
       ▼                                                                                    │
  [Layer 1: 기계적 기본선 체크 (자동 · 토큰 0)] ── 실패 시 에러 요약 즉시 반환 ───────────────┤
   • 빌드·타입체크 통과, 기존 테스트 회귀 0건, 변경분 린트 0건                                 │
       │ (통과 시에만 호출 → 토큰 절감)                                                       │
       ▼                                                                                    │
  [Layer 2: Built-in Verifier StepAgent (독립 클린 세션 · 판정 전용, 코드 수정 금지)]          │
   • 입력: Goal/Spec + 변경 Diff + Layer 1 실행 결과                                         │
   • 판정: 요구사항 누락·엣지케이스·의도 불일치 철저 검증                                      │
       │                                                                                    │
       ├── 미달 (재시도 가능): 구조화된 Fix Report 발행 (같은 오답 반복 차단) ───────────────┘
       ├── 한계 도달 (최대 N회 · 동일오류 반복 · 비용 상한): 실패 상태 그대로 투명 보고 (미달 기준·원인·시도 이력)
       └── 달성 시: 정제 결과 memory.md 반영 + dashboard.md [DONE] ──▶ 다음 Step
```

* **2계층 종료 조건 설계 (작업 유형별 공통화 + 유연성 확보)**:

| 계층 | 역할 | `profile: code` (코딩 · 테스트 · 버그 수정) | `profile: analysis` (Anomaly Analysis) |
| :--- | :--- | :--- | :--- |
| **Layer 1**<br>*(공통 기본선 · 기계적 자동)* | 최소 완결성 보장<br>*(토큰 0 · 선행 필터)* | • 빌드·타입체크 통과, 기존 테스트 회귀 0건, 변경분 린트 0건 *(DP-02 영속 메모리 명령 자동 호출)* | • 인용 근거(파일·시각·에러문구) 원본 실존 확인(환각 0건), 필수 리포트 스키마 충족, 대상 범위 스캔 확인 |
| **Layer 2**<br>*(Built-in Verifier StepAgent)* | Goal 충족 여부<br>독립 철저 판정 | • 정형: 커버리지 ≥ N%, 재현 테스트 PASS, 구 API 0건<br>• 비정형: Spec(AC) 테스트 + Verifier의 `Spec vs Diff` 대조 및 누락·엣지케이스 점검 | • 이상 패턴·이벤트 분류 및 원인-결과 타임라인 매핑<br>• Verifier 클린 세션의 가설 반증·근거 교차 확인 *(확증 편향 차단)* |

## 2. DP-02. 문제 정의 — 사내 맥락 & 레포 영속 메모리

### 문제 상황 `(반복적인 초반 환경조사 지연과 세션 간 맥락 단절)`
* **[사내 사용자 VOC]** Craft 실행 시마다 에이전트가 초반에 **빌드·테스트 실행 방법, 개발 환경, 레포 구조 및 사내 규칙을 파악하느라 긴 시간과 시행착오를 반복**하며, 사내 컨벤션 미숙지로 리뷰 수정도 빈번하게 발생
* **[기존 메모리 구조의 한계]** 올해 구축한 `memory.md`는 **단일 작업(실행 세션) 내** Step 간 전달용으로 종료 시 소멸되어, 어렵게 파악한 환경 설정·코드베이스 구조·리뷰 피드백이 다음 실행으로 이어지지 못하고 매번 원점부터 재탐색

### 해결방법 검토
* **[기존 방식의 한계: 정적 규칙 문서 수동 작성]** 개발자가 레포별 환경·규칙 문서(`README`, rule 파일)를 수동 관리하는 방식은 코드·환경 변경을 따라가지 못하고, 문서 비대화 시 토큰 낭비 및 지침 누락 유발
* **[외부 AI 도구 동향: 레포/팀 단위 영속 메모리 및 선별 맥락 주입]** 실행 중 검증된 **환경·빌드·테스트 명령, 레포 아키텍처, PR 리뷰 피드백**을 프로젝트 단위 영속 지식으로 자동 축적하고, 작업 초반에 필요한 맥락만 즉시 주입(Context Engineering)하는 추세

### 미해결 시 위험 `(영속 메모리 및 맥락 축적 부재 시)`
* 동일 레포에서 반복 실행해도 매번 **초반 환경조사에 따른 실행 지연·시행착오·토큰 낭비**가 되풀이되어 개발자 체감 속도 및 채택률 저하
* 사내 규칙과 리뷰 피드백이 누적되지 않아, 외부 범용 AI 도구 대비 **사내 프레임워크만의 품질 우위(해자) 확보 불가**

### 핵심 설계 문제
> **“매 실행 초반의 환경조사 시행착오를 없애고, 검증된 환경 정보·사내 규칙·리뷰 피드백이 쓸수록 축적되어 빠르고 ‘우리 회사 코드답게’ 작업하게 하려면 어떻게 설계해야 하는가?”**
> ▶ 단일 세션용 `memory.md`를 **레포/팀 단위 영속 지식(Persistent Memory)**으로 확장하고, 실행 초반 **환경·맥락 즉시 주입 및 작업 후 자동 갱신 파이프라인** 설계

## 3. DP-03. 문제 정의 — 외부 에이전트(Tool) · 모델 통합 바인딩 (Agent Driver Adapter)

### 문제 상황 `(Cline SDK 단일 런타임 종속 및 외부 에이전트 단절)`
* **[사내 사용자 VOC]** 사내에 Claude Code, Codex 등 고성능 외부 코딩 에이전트(Tool)가 공존하고 있으나, 기존 프레임워크는 Step별 사내 모델 지정만 가능해 **외부 에이전트 툴과 그 특정 모델(예: Claude Code + 특정 모델)을 워크플로우에 조합해 쓸 수 없음**
* **[기존 L3/L4 구조의 한계]** 단순 모델 API(L4)가 아니라 **자체 실행 루프·편집 도구·프롬프트가 최적화된 외부 에이전트 툴 자체(L3)**를 실행기로 꽂아야 성능이 극대화되나, 현재는 `@cline/agents` SDK 단일 런타임에 고정되어 외부 에이전트의 강점을 흡수 불가

### 해결방법 검토
* **[기존 방식의 한계: 단일 SDK 및 모델 API 교체에만 의존]** Cline 단일 런타임만 고수할 경우, 이미 Claude Code·Codex를 사용하는 개발자들의 워크플로우와 이원화되어 사내 프레임워크 도입 장벽으로 작용
* **[외부 AI 도구 동향: Agent-Agnostic 통합 하네스]** 특정 에이전트 SDK에 종속되지 않고, 공통 오케스트레이션·메모리·보안 정책 아래 **작업 성격별 최적 에이전트 툴과 모델 조합(Claude Code · Codex · 자체 Cline-SR)을 플러그인처럼 바인딩**하는 구조로 전환

### 미해결 시 위험 `(단일 런타임 종속 시)`
* 개발자들이 외부 에이전트 도구로 분산·이탈하면서 **올해 구축한 Craft · Blackboard · 보안 통제 자산의 사내 채택률 저하**
* 외부 AI 도구별 파편화 사용이 심화되어 **사내 맥락(DP-02) 단절 및 전사 차원의 워크플로우 표준화 불가**

### 핵심 설계 문제
> **“올해 구축한 Craft·메모리·보안 통제 자산을 유지하면서, Step별로 사내 모델(Cline-SR)과 외부 에이전트 툴·모델 조합(Claude Code/Codex 등)을 자유롭게 바인딩하려면 어떻게 설계해야 하는가?”**
> ▶ L2~L3 사이에 **Agent Driver Adapter 계층**을 도입하여, YAML 선언만으로 Step별 사내 모델과 외부 에이전트(Tool)·모델 조합을 동적 바인딩하는 통합 하네스 구조 설계

#### 참고: 외부 에이전트 바인딩 시 층위 구분 및 Orchestrator 역할 분리
* **단순 모델 추가(L4) vs DP-03(L3)**: L4는 모델 API만 교체(실행 루프는 Cline 고정)하는 반면, DP-03은 **외부 에이전트 툴 자체와 그 모델 조합을 L3 실행기로 바인딩**
* **흐름 제어 (Deterministic Orchestrator → L2 코드)**: Craft YAML 파싱, Executor–Verifier 루프(재시도/종료/실패 보고), Blackboard 입출력, 예산/보안 가드레일(각 에이전트 네이티브 권한 옵션으로 번역)
* **판단/계획 (Cognitive Role → L3 Driver Adapter)**: 설계·분석·리뷰 등 판단이 필요한 Step도 Driver Adapter를 통해 작업 성격별 최적 에이전트(Claude Code / Codex / Cline-SR) 선택 호출

## 4. DP-04. 문제 정의 — 지능형 도구 · MCP · Skill 동적 라우팅 (Dynamic Tool Routing)

### 문제 상황 `(정적 이름 기반 화이트리스트의 누락 위험과 MCP · Skill 확장 병목)`
* **[현재 도구 통제 구조의 한계]** Step별 사용 도구(Tool · MCP · Skill)를 YAML에 **이름 기반 화이트리스트**로 수동 선언하고 런타임에서 통제하고 있으나, **YAML 수동 편집 중 오타·필요 도구 누락**이 발생하거나 실제 필요한 도구가 **다른 레지스트리/경로에 존재**해 작업이 막히거나 헛도는 사례 발생
* **[MCP · Skill 확장 시 구조적 병목]** 사내 MCP 서버와 Skill 자산이 늘어날수록 사용자가 모든 도구 이름을 외워 YAML에 수동 매핑하기 어렵고, 반대로 전체 도구를 일괄 주입하면 **컨텍스트 오염(Context Rot)과 토큰 비용 급증** 유발

### 해결방법 검토
* **[기존 방식의 한계: YAML 화이트리스트 수동 관리 및 일괄 도구 주입]** 이름 문자열에 의존하는 정적 화이트리스트는 오타·누락에 취약하며, MCP·Skill 수가 증가할수록 작성·유지보수 부담이 급증
* **[외부 AI 도구 동향: Progressive Context Disclosure & Decision Models (Thoughtworks Radar Vol.35)]**
  * **Progressive Context Disclosure (`Adopt`)**: 모든 도구·MCP·Skill을 처음부터 컨텍스트에 싣지 않고, 가벼운 탐색(Discovery) 단계를 거쳐 **현재 작업에 필요한 것만 동적으로 로드**하는 패턴이 업계 표준으로 정착
  * **Decision Models (`Assess`, 대표 사례: TypeSafe AI Jev, Laya, Nimble, Kev)**: 텍스트 생성 대신 `choice` / `Score` / `Noul`(참·거짓 확률) 형태로 **구조화된 값과 보정된 확률(Calibrated Probability)**을 고속·저비용으로 반환하는 판별형 모델을 **도구·MCP·Skill 라우팅**에 탐색·적용하는 추세

### 미해결 시 위험 `(동적 도구 라우팅 부재 시)`
* 필요한 도구·MCP·Skill이 누락된 상태로 Step이 실행되어, 해결 불가능한 재시도와 불필요한 토큰 낭비 유발
* 사내 MCP·Skill 자산을 늘려도 개발자가 YAML에 일일이 연결하지 못해 **도구 생태계 확장 효과가 현장 채택률로 이어지지 못함**

### 핵심 설계 문제
> **“기존 화이트리스트 기반 런타임 통제를 유지하면서도, 도구 · MCP · Skill이 확장될 때 오타·누락 없이 작업에 가장 적합한 도구를 확률적으로 추천·바인딩하려면 어떻게 설계해야 하는가?”**
> ▶ 정적 화이트리스트를 **보안 허용 경계(Allowed Pool)**로 유지하고, 그 위에 **통합 레지스트리(Tool · MCP · Skill) + 확률 기반 동적 라우터(Decision Model 탐색·PoC)**를 도입하여 누락·오타 보정과 선별 주입 구현

#### 참고: 정적 화이트리스트 → 확률 기반 도구 · MCP · Skill 동적 라우팅 구조
```text
  [Craft YAML (보안 허용 경계: Allowed Pool)] + [통합 레지스트리 (Tool · MCP · Skill)]
                                    │
                                    ▼
             [Pre-flight Tool / MCP / Skill Router]
              1) 결정론적 검증: 통합 레지스트리 대비 퍼지 매칭으로 YAML 오타·경로 불일치 즉시 보정
              2) 확률 기반 추천 (Decision Model 탐색 — 예: Jev의 Noul / choice):
                 • 작업 목표(Goal) 대비 도구·MCP·Skill 적합 확률 산출
                 • 고확신 + 허용 풀 내 ──▶ 자동 동적 바인딩 (Progressive Context Disclosure)
                 • 경계 구간 / 풀 외 필요 도구 ──▶ 누락 경고 및 사용자 확인 유도
                                    │
                                    ▼
             [Step 실행 (필요 도구 · MCP · Skill만 선별 주입)]
```

* **단계적 검증 전략**: Decision Models는 Radar `Assess` 단계이므로, 초기에는 **임베딩 기반 시맨틱 검색 + 경량 분류기** 베이스라인으로 동적 도구 추천을 구축하고, **Jev 등 Decision Model**과 정확도·지연·비용을 병행 벤치마크

## 5. DP-05. 문제 정의 — 결과 중심 KPI · 모델별 토큰 분산 & 성과 진단 (Observability & Evaluation)

### 문제 상황 `(단순 이벤트 집계 중심의 한계와 완결성·모델 분산 가시성 부재)`
* **[현재 측정 구조의 한계]** 현재는 **사용 빈도(실행 이벤트 집계)** 수준의 활동 지표만 수집하고 있어, 실제로 **개발자 재작업이 얼마나 줄었는지, 어느 Step에서 실패·지연이 반복되는지, 사내/외부 모델 간 토큰이 의도대로 분산되고 있는지** 정량적으로 파악할 수 없음
* **[고도화 효과 증명 불가]** Craft는 Step 격리 구조 특성상 단순 토큰 총량 절감이 목적이 아니라 **높은 완결성과 합리적인 모델 분산**이 핵심이나, DP-01~04 도입 전후의 **PR 완결성·초반 탐색 단축·모델별 토큰 분산 효과**를 객관적 수치로 입증할 측정 기반이 부재함

### 해결방법 검토
* **[기존 방식의 한계: 실행 횟수 · AI 코드 생성 비율 같은 활동 지표(Activity Metrics)]** Thoughtworks Radar Vol.35(`41. Coding throughput as a measure of productivity`, `Caution`)는 단순 실행량·코드 생성 비율·토큰 총량을 생산성 지표로 삼으면 굿하트의 법칙(허수 성과)에 빠진다고 경고. JetBrains 2026 조사에서도 대기업 매니저 51%가 토큰 총량만 추적하고 순시간 절감은 측정하지 못해 **대기업 AI ROI 만족도가 34%에 그침**
* **[외부 AI 도구 동향: Path-to-Production 기반 결과 지표 & Context Profiling (Thoughtworks Radar Vol.35)]**
  * **Path-to-Production Mapping (`Adopt`, 15p)**: 코드 작성 속도가 아니라 실제 PR 완결·머지까지 End-to-End 흐름에서 병목이 발생하는 구간을 진단
  * **Context Profiling (`Assess`, 23p) & `AgentsView` (`Assess`, 44p)**: 세션별로 어느 Step·도구·모델에 토큰이 배분되고 있는지(컨텍스트 오염·모델 편중·캐시 히트율)를 정밀 프로파일링해 최적화 근거로 활용하는 추세

### 미해결 시 위험 `(결과 중심 성과·모델 분산 진단 체계 부재 시)`
* 사용 횟수는 늘어도 실제 PR 완결성·생산성 개선 여부를 증명하지 못해 **경영진 대상 2027년 과제 ROI 설득 및 지속 투자 확보 실패**
* 특정 외부 고가 모델에 토큰이 과도하게 쏠리거나 특정 Craft·Step에서 실패가 반복되어도 보이지 않아 **감(직관)에 의존한 비효율적 튜닝 반복**

### 핵심 설계 문제
> **“단순 사용 빈도 집계를 넘어, DP-01~04의 실제 PR 완결성·탐색 단축·모델별 토큰 분산 효과를 정량적으로 진단하고 하네스 개선으로 되먹임하려면 어떻게 설계해야 하는가?”**
> ▶ L2 Orchestrator에 **① 결과 중심 실행 텔레메트리(완결률·재시도·실패 유형) · ② 모델별 토큰 분산 & 컨텍스트 프로파일러(사내/외부 모델 배분·탐색/도구 비중) · ③ Path-to-Production 병목 진단 대시보드**를 내장하여 측정과 개선을 단일 루프로 연결

#### 참고: 단순 이벤트 집계 → L2 내장 성과·모델 분산 프로파일링 체계

```text
       │
       ├── ① 완결성 지표 (DP-01 연계): 1차 통과율 · 평균 재시도 횟수 · Layer 1/2 실패 원인 분포

```

### 오해 방지 프레이밍 (QA/검증 오해 차단)
