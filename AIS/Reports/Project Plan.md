### 1. 과제명
**전문가 에이전트 실행을 위한 Cline^HD 하네스 설계**

---

### 2. 과제 개요
Cline^HD는 테스트 에이전트 등을 제공하고 있으나, 단일 루프 수행 방식 및 컨텍스트 윈도우 제약으로 인해 복잡한 작업의 품질 유지에 한계가 있으며, 범용 프롬프트 및 도구 적용 구조로는 도메인 및 목적별 특화 에이전트를 유연하게 지원하기 어려움. 
이를 해결하기 위해 작업을 단계별(Step)로 분할하고 전용 프롬프트·도구·기초정보를 패키징한 '전문가 에이전트' 실행 구조를 설계하고자 함.
이를 통해 작업 맥락과 응답 품질을 안정적으로 유지하고, 도구 권한과 범위를 최소화하여 안전하고 신뢰성 높은 실행 환경을 제공하고자 함.


---

### 3. 추진배경 / 필요성
- **단일 에이전트 루프의 컨텍스트 비대화 및 복구 한계**: 태스크 진행에 따라 대화 및 실행 이력이 누적되면 컨텍스트 윈도우가 과부하되어 지시 불이행 및 환각이 증가하며, 오류 발생 시 이전 맥락 오염으로 인해 자가 복구가 어려움.
- **프롬프트 기반 소프트 통제의 한계**: "파일 수정 금지"와 같이 프롬프트 지시로만 역할을 제한할 경우, LLM의 비결정론적 특성과 프롬프트 인젝션에 취약함. 이로 인해 비인가 파일 쓰기, 셸 실행 등의 보안·안전 위험을 원천 차단하기 어려움.
- **다양한 제품군 도메인 및 개발 라이프사이클별 최적화 요구**: 사내 다양한 제품군 도메인과 개발 라이프사이클(아키텍처 설계, 코드리뷰, 로그 분석, 테스트 작성 등)에 따라 최적의 프롬프트, 도구 셋, 기초 정보, 검증 기준이 상이하여 이에 특화된 전문가 에이전트 구조가 요구됨.
- **사내 서빙 모델 활용 균형 및 인프라 효율화 니즈**: 특정 모델에 사용량이 쏠리는 현상을 방지하고, 사내 서빙 모델 3종을 태스크 특성에 맞게 사용자가 지정·활용할 수 있도록 지원하여 사내 AI 인프라 자원의 효율성을 극대화할 필요가 있음.

### 4. 과제 상세 (Work to do)

#### 가. 최종 산출물 및 핵심 목표
- **전문가 에이전트 패키징 및 실행 하네스 설계**: 도메인 특화 프롬프트·도구 셋 구성 및 Step 분할 실행을 통해 태스크 완료율 90% 이상, 토큰 비용 증가율 10% 이하 달성.
- **안전하고 예측 가능한 런타임 실행 제어 환경 구축**: 런타임 훅 기반의 도구 접근 권한 제어 체계를 확립하여 비인가 도구 호출 없는 제어 성공률 100.0% 달성.
- **사용자 정의 확장 및 모델 최적 배분 체계 확보**: 사용자가 목적에 맞게 프롬프트, 도구, 사내 서빙 모델 3종을 직접 조합·지정하여 전문가 에이전트를 확장하고 인프라 자원을 최적화할 수 있는 인터페이스 설계.

#### 나. 연구 내용 및 방법 (핵심 추진 항목)
1. **Cline SDK 실행 하네스 구조 분석 및 런타임 훅 제어 설계**:
   - SDK의 `AgentRuntime`, `SessionRuntime`, `Runtime Hooks`, `Event Subscription` 메커니즘을 분석하여 에이전트 실행 수명주기 관리 및 런타임 레벨의 도구 접근 권한 제어 구조 설계.
2. **Orchestrator - Step Agent 기반 계층적 작업 분할 및 맥락·모델 관리**:
   - 전체 워크플로우를 조율하는 Orchestrator와 단위 작업을 전담하는 Step Agent 구조를 설계하고, Step 간 필수 맥락/결과물(Memory)만 선별 전달하여 컨텍스트 비대화 방지 및 복구 탄력성 확보.
   - Step 특성별 난이도(예: 심층 분석은 고성능 모델, 요약/Report 작성은 경량 모델 등)에 따라 사내 서빙 모델 3종을 유연하게 지정·호출하는 단계별 모델 매핑 구조 설계.
3. **동적 프롬프트 조립(Assembly) 및 전문가 에이전트 구성 프레임워크 설계**:
   - 사용자 입력, 작업 기초정보(Prerequisites), 도구 명세, 실행 규칙을 유기적으로 합성하는 동적 프롬프트 조립 방식을 설계하고, 사용자 정의 전문가 에이전트 확장 인터페이스 제공(Test 작성, 로그 분석 등 도메인별 전문가 에이전트 적용·검증).

#### 다. 목표 달성을 측정하기 위한 구체적인 Metric

| 구분 / AI 품질속성 (ISO/IEC 25059) | 핵심 개념 및 선정 사유 | 구체적 측정 메트릭 (Metric) 및 산출식 | 정량적 목표 수준 및 측정 방법 |
| :--- | :--- | :--- | :--- |
| **[메인 1] Performance Efficiency<br>(수행 효율성 - 하네스 성능)** | 단일 루프 대비 컨텍스트 비대화를 방지하고 토큰 및 자원 소비를 최소화하면서 태스크를 완수하는 능력 | • **Task Success Rate (태스크 완료율)**<br>  - 산출식: $\left(\frac{\text{성공 Task 수}}{\text{전체 Task 수}}\right) \times 100$<br>• **Token Cost per Request (요청당 토큰 비용)**<br>  - 산출식: $\frac{\sum(\text{Input Token} + \text{Output Token})}{\text{요청 수}}$ | • **목표 1 (완료율)**: Task Success Rate 90% 이상<br>• **목표 2 (비용 효율)**: 동일 벤치마크 태스크에서 단일 루프 대비 Token Cost per Request 동등 이하 수준 달성<br>• **측정**: 동일 벤치마크 태스크 세트에서 단일 루프와 새 구조 각각의 Task Success Rate 및 Token Cost per Request를 측정·비교 |
| **[메인 2] Controllability<br>(제어 가능성)** | 런타임 하네스가 전문가 에이전트의 도구 접근 및 권한을 엄격히 제어하여 의도한 안전 상태를 완수하는 능력 | • **제어 성공률 (Control Success Rate)**<br>  - 산출식: $\left(\frac{\text{비인가 도구 호출 없이 의도한 제어 목적을 달성한 횟수}}{\text{전체 제어 시도 태스크 수}}\right) \times 100$ | • **목표: 제어 성공률 100.0%**<br>• **측정**: Read-Only 전문가 에이전트에 비인가 도구(파일 수정/셸 실행) 호출 지시 주입 시 런타임 훅 차단 및 정상 완료 여부 검증 |
| **[메인 3] Functional Correctness<br>(기능 정확성)** | Step 분할 구조에서도 단일 루프 대비 동등한 분석·검증 품질을 유지하는 능력. Step 분할 시 전체 맥락 단절로 인한 정확도 저하 리스크가 존재하므로, 정확도를 희생하지 않고 효율성·제어성을 확보함을 입증 | • **F1-Score**: $2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$<br>  *(Precision = $\frac{TP}{TP+FP}$, Recall = $\frac{TP}{TP+FN}$)*<br>• **F1 보존율 (F1 Preservation Rate)**<br>  - 산출식: $\frac{F1_{\text{새구조}}}{F1_{\text{단일루프}}} \times 100$<br>  *(TP: 결함 주입 코드에서 생성 TC가 Fail로 정상 검출, FN: 결함 주입 코드에서 TC가 Pass/미검출, FP: 정상 코드에서 TC Fail 오탐)* | • **목표: F1 보존율 95% 이상** (단일 루프 대비 동등 이상 품질 유지)<br>• **측정**: 동일 벤치마크 태스크 세트에서 **단일 루프와 새 구조를 모두 실행**하여 F1-Score 상대 비교<br>• **측정 대상 (정확성 검증 벤치마크)**:<br>  ① **Test 작성 에이전트**: 결함 주입(Mutation Testing) 코드 대상 TC 생성 및 실행 시, 주입된 결함을 정확히 Fail로 검출(Kill)하는지 및 정상 코드 Pass 여부 기반 F1-Score 평가<br>  ② **로그 분석 에이전트**: 정답 라벨이 부착된 대용량 로그 데이터셋에서 장애/비정상 로그 탐지·분류 정확도 평가 |
| **[선택 분석 / Optional]<br>Performance Efficiency<br>(수행 효율성 - 모델 최적화)** | 단일 모델 의존을 탈피하고 Task 및 Step(탐색, 분석, 보고 등) 특성에 따른 사내 모델 3종의 최적 조합을 도출하는 능력 | • **1) 품질(Quality)**: Task / Step Success Rate<br>• **2) 비용(Cost)**: Token Cost per Step/Request<br>  - 산출식: $\frac{\sum(\text{Input} + \text{Output Token})}{\text{요청 수}}$<br>• **3) 속도(Speed)**: Latency (Step/End-to-End 소요시간) | • **선택 분석 (최적 모델 매핑)**: Task 및 세부 Step(Investigate $\rightarrow$ Analysis $\rightarrow$ Report)별로 사내 모델 3종의 품질·비용·속도를 비교 측정하여 **Step/Task 특성별 최적 모델 선정 가이드라인 수립 (수행 여건에 따라 선택적 진행)** |

### 5. 과제성과 / 기대효과
- **과제수행을 통해 예상되는 기술 수준 향상**:
  - **에이전트 하네스 엔지니어링 기술 내재화**: 프롬프트 기반의 단순 제어를 넘어 런타임 하네스 엔지니어링을 통한 안전한 도구 권한 제어 및 실행 신뢰성 확보.
  - **오픈소스 Cline 대비 차별화된 독자 Feature 확보**: 오픈소스의 단일 루프 한계를 넘어선 'Step 오케스트레이션' 및 '런타임 도구 제어' 등 사내 환경에 특화된 고유 에이전트 기능 및 아키텍처 자산 내재화.
- **사업 성과 측면의 기대효과**:
  - **사내 AI 인프라 활용 효율화**: 특정 모델로의 사용량 쏠림을 완화하고 사내 서빙 모델 3종의 고른 활용을 지원하여 전사 인프라 운영 최적화.
  - **사내 개발 생산성 향상 기여**: 2026년 하반기 Cline^HD 공식 릴리즈에 본 하네스 구조를 반영하여 사내 개발자의 생산성 및 작업 품질 향상에 기여.
